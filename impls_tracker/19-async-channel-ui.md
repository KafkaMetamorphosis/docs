## Decisions

### Q1 — deliverable number for a UI-only follow-up
- **Asked by:** claude   **Answered by:** user (operator, up front)
- **Answer:** **19**, its own stacked `impl/NN-slug` branch, its own PR, its own
  plan doc + tracker, based on `impl/11-cluster-and-agent-config` (head
  `9125050`). Verified: 01–18 are taken, so 19 is the next free number, and the
  plan has no separate convention for UI-only follow-ups — deliverable 08 already
  set the precedent that console work is its own numbered deliverable rather than
  an amendment to the backend one it completes.

### Q2 — scope of this pass
- **Asked by:** claude   **Answered by:** user (operator, up front)
- **Answer:** **channel CRUD + lifecycle only** — name, `type`,
  `channel_partitions`, `labels`, pause / resume / delete. **Access-policy UI is
  deferred to deliverable 17.** No policy statement editor, no `accessPolicy` on
  create (empty = closed channel is the correct zero-trust default), no policy
  panel, and no "Clients with access" panel (`ListChannelClients` returns
  `UNIMPLEMENTED` until 17). The detail page carries a short non-interactive
  "managed in a later release" placeholder note instead.

### Q3 — e2e coverage
- **Asked by:** claude   **Answered by:** user (operator, up front)
- **Answer:** add `webconsole/e2e/channels.spec.ts` as a smoke mirroring
  `console.spec.ts`'s structure, including the same `beforeAll` health-check skip
  guard: sign in → create a channel → see it in the list → open detail → pause →
  assert paused.

### Implementation choices (not asked)
- **No proto or codegen work** — `AsyncChannelService` and every message shape
  were generated by deliverable 10; `schema.d.ts` already carried them.
- **`ChannelEdit` is labels-only.** `UpdateAsyncChannel` masks `labels` alone, so
  the form renders `type` and `channel_partitions` as read-only facts and never
  puts either in a mask. Tested explicitly (they must not be inputs).
- **The detail page does not poll.** The cluster detail page polls at 4s because
  provider status trends toward `READY` on its own; nothing about a channel
  changes server-side without an operator action, so a poll would be noise.
  Noted in the plan as something placement (13) will want once shards exist.
- **No pagination.** `ListAsyncChannels` supports `page.pageSize` /
  `page.pageToken`, but no console list paginates yet; adding it on one screen
  only would be inconsistent. Flagged in the plan as its own cross-cutting change.
- **Sidebar** — the single disabled "Coming with the feature" span under Async
  Channels became a real `Channels` link plus a still-disabled `Clients` entry,
  matching the demo IA (`async-channels.html`) and the operator's instruction to
  leave Clients alone for deliverable 16 / 17. The group now defaults to `open`.
- **`Home`** already had resource stat cards, so it gained an Async Channels stat
  and a service card.

## Notes / deviations

- **One test was rewritten after it failed honestly.** The first version of
  "rejects a channel-partition count below 1" asserted the submit handler's
  `role="alert"`, but jsdom enforces the input's native `min={1}` constraint and
  blocks submission before the handler runs — so the alert never appeared. The
  guard is still real defence-in-depth (a direct `submit` event bypasses
  constraint validation), so the test now uses `fireEvent.submit` to reach it,
  and a separate test asserts the declarative `type` / `min` / `step` /
  `required` / default-value constraints. Both layers are covered, neither is
  asserted where it cannot run.
- No `DECISIONS.md` entry was added. Deferring the policy UI to 17 is a scoping
  choice that follows directly from the existing ADR-API-009 / deliverable-17
  split rather than a new architectural decision, and it is already recorded in
  the plan doc and here. Raised for the operator to overrule if they want an ADR
  line anyway.
