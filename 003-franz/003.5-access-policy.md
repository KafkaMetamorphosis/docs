# Channel Access Policy

Status: **ready**

Shapes & RPCs: [`async_channel.proto`](../../franz/api/franz/v1/async_channel.proto) —
`AccessPolicy`, `AccessPolicyStatement`, `Effect`, `Principal`,
`ChannelClientAccess`; `AsyncChannelService.SetAccessPolicy` /
`ListChannelClients`. `Permission` is in
[`common.proto`](../../franz/api/franz/v1/common.proto).

## Concepts

The **access policy** is the **data-plane** authorization model: whether a
**Client** (`003.10`) may **read from** or **write to** an Async Channel through
the Franz SDK. It is **not** about console/API calls — those are
`003.2-api-authorization.md`.

- **One `AccessPolicy` document per channel**, embedded in the `AsyncChannel` and
  replaced wholesale via `SetAccessPolicy` (never through `UpdateAsyncChannel`).
- A policy is an **ordered list of statements**; each is
  `{ effect, principal, permissions }`.
- **Zero trust**: a client with no matching `ALLOW` has no access. An empty policy
  denies everyone.
- Modelled on an AWS-style resource policy: broad grants narrowed by explicit
  denies.

## Key shapes

- **`AccessPolicyStatement`** — `effect` (`ALLOW` / `DENY`, `UNSPECIFIED`
  rejected), `principal`, `permissions` (non-empty subset of
  `PERMISSION_READ` / `PERMISSION_WRITE`).
- **`Principal`** — `client_frn` and/or `labels` (a label selector, `003.1`
  grammar). A statement matches a client when **`client_frn` matches (if set)
  OR the selector matches the client's labels (if set)** — at least one of the
  two must be set. `client_frn` and selector *values* accept the `*` glob
  (`003.1`).
- **`ChannelClientAccess`** (`ListChannelClients` result) — a resolved row:
  `client_frn`, `client_labels`, `effective` permissions, `matched_by` (which
  statement decided it).

## Evaluation

For a `(client, action)` pair, where `action` is READ or WRITE:

1. Take the statements whose `principal` matches the client **and** whose
   `permissions` include `action`.
2. If **any** matched statement is `DENY` → **denied**.
3. Else if **any** matched statement is `ALLOW` → **allowed**.
4. Else → **denied** (zero trust).

Explicit `DENY` always wins regardless of statement order; order in the document
is not significant to the outcome. READ and WRITE are evaluated independently — a
client can be allowed one and denied the other.

### Worked example

```
statements:
  - effect: ALLOW
    principal: { client_frn: "frn:acme:client:xpto-*" }
    permissions: [READ]
  - effect: DENY
    principal: { client_frn: "frn:acme:client:xpto-blah" }
    permissions: [READ]
```

`xpto-1` → READ allowed. `xpto-blah` → READ denied (the `DENY` beats the wildcard
`ALLOW`). Any client not matching `xpto-*` → denied (zero trust). Nobody has WRITE.

## Invariants

- Exactly one policy per channel; it always exists (possibly empty).
- Every statement: `effect ≠ EFFECT_UNSPECIFIED`, `permissions` non-empty, and
  `principal` has at least one of `client_frn` / `labels` set — else
  `INVALID_ARGUMENT`.
- The policy is replaced atomically by `SetAccessPolicy`; there is no per-statement
  add/remove RPC.
- A statement referencing a `client_frn` that does not currently resolve to a
  Client is **valid** (it simply matches nothing) — supports pre-provisioning and
  survives client deletion.
- Statement count is capped; exceeding it is `RESOURCE_EXHAUSTED` (`003.1`). The
  cap value is an open question.

## Cross-entity behavior

- **Client** (`003.10`) carries **no permission of its own** — the channel policy
  is the sole source of truth. `ListClientChannelAccess` is the reverse view
  (which channels a client can reach).
- **Channel pause / delete** (`003.4`) does not change the policy; a paused
  channel still evaluates the same way, but the SDK data path is unavailable.
- **Governance** (`003.8`) does not write access policies — no `ActionKind`
  touches statements.
- **Client deletion** — `client_frn`-matched statements go dormant (nothing
  resolves to that FRN; the FRN is not reclaimed, `003.10`); selector-matched
  statements are unaffected and will match any future client whose labels fit.

## Open questions

1. **SDK enforcement point** — is the check at connection / subscription
   establishment, per message, or both; and what happens to a live connection when
   the policy changes (dropped, downgraded on next operation, or unaffected until
   reconnect). Ties into the client-auth ADR.
2. **Statement cap** — the concrete maximum number of statements per policy.
3. **Selector-match cost** — `ListChannelClients` must evaluate every statement
   against every Client in the realm; whether that needs a bound or an async
   materialised view.
4. **`matched_by` for multi-match** — when several statements match, what
   `ChannelClientAccess.matched_by` reports (the deciding DENY, or the full set).
