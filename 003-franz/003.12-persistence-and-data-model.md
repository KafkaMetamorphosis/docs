# Persistence and Data Model

Status: **draft**

Shapes: entity fields are authoritative in `../../franz/api/franz/v1/*.proto`;
this document owns **how they are stored**.

## Concepts

Franz's only datastore is **PostgreSQL**. It holds the *declared* state of every
fleet resource plus the audit and telemetry records Franz receives. It does **not**
hold Kafka's own state (that lives in the real clusters) or generated code.

The database is reached only through
`franz/pkg/franz/adapters/out/postgres/`, which implements the `core/ports/out`
repository interfaces (`../002-monorepo-structure/`). `core/domain` and
`core/usecases` contain no SQL and no driver imports.

## Storage choices (cross-cutting)

- **One row per resource**, surrogate primary key `id uuid` (v7, time-ordered).
  The domain identity is `(realm_id, name)` — a `UNIQUE` constraint — and `orn` is
  a second `UNIQUE` column, set once at insert (`003.1`).
- **`name` is never reused.** The `(realm_id, name)` constraint is unconditional;
  a soft-deleted row keeps its name and ORN.
- **Enums are `text` + `CHECK`**, not PostgreSQL `enum` types — the proto enum is
  the source of truth and a text column evolves without a migration. Stored as the
  proto short form (`ACTIVE`, `PAUSED`, `READY`, …).
- **Timestamps are `timestamptz`.** `created_at` / `updated_at` on every table.
- **Maps → `jsonb`.** `labels`, `cluster_configuration`, `topic_configuration`
  are `jsonb` objects with a **GIN index** so label-selector filtering (`003.1`)
  can push down to Postgres.
- **Repeated / document fields → `jsonb`.** `connection_strings` (array),
  `access_policy` (one document, replaced wholesale by `SetAccessPolicy`),
  `actions` lists.
- **Realm scoping.** Every table carries `realm_id` (FK → `realm`); every query
  filters on it. There is no cross-realm read path.
- **Soft delete.** `state = 'DELETED'` rows are retained. Repositories exclude
  them by default; a direct `Get` still returns one so the caller can raise
  `FAILED_PRECONDITION` (`003.11`).

**Derived views** — `ChannelClientAccess` / `ClientChannelAccess` (`003.5`,
`003.10`) are **not tables**. The usecase loads the channel `access_policy` and
the candidate `client` rows and evaluates the policy in Go (wildcard and selector
matching live in the domain).

## Materialized topic configuration

`003.3` / `003.6`: editing `cluster_configuration` affects only *future* shards;
existing shards keep the configuration they were created with. So `kafka_topic`
stores two columns:

- `topic_configuration` — the per-shard override (proto
  `KafkaTopic.topic_configuration`).
- `materialized_configuration` — `cluster_configuration` ⊕ `topic_configuration`,
  computed and **frozen** when the shard is created or its desired state changes.
  A later `cluster_configuration` edit does not touch it. This is what an agent
  reconciles against.

## Concurrency

- **Resource updates** use optimistic concurrency:
  `UPDATE … WHERE id = $1 AND updated_at = $2`; zero rows ⇒ lost-update conflict
  ⇒ `ABORTED`.
- **`kafka_topic.generation`** is the separate domain token (`003.6`), bumped on
  every desired-state change; agents echo it so Franz rejects stale reports.
- **Compound operations run in one transaction** — `CreateAsyncChannel` inserts
  the channel, its `channel_partitions` `kafka_topic` rows, and the placement
  result atomically.

## Migrations

**Flyway**, `franz/migrations/`. While Franz is pre-production a single
`V1__init.sql` is edited in place — no new versioned files until the schema is
frozen. `pkg/gen/go` is generated, not migrated.

## Open questions

1. **Query layer** — `pgx` + `sqlc` (typed queries from hand-written SQL) vs.
   `pgx` + hand-written vs. an ORM. Shapes `adapters/out/postgres`.
2. **`indicator_sample` history** — latest-only vs. a bounded time series;
   retention; whether governance ever needs a window rather than a point value.
3. **Client deletion** — a `deleted_client_orn` reservation ledger vs. adding a
   `state` / `DELETED` column to `client` (`003.10` / `003.11`).
4. **`realm` bootstrap** — how the first realm and its `slug` are created before
   any API call is authorized (`003.1`).
5. **Selector push-down** — how much of the `003.1` grammar (`IN`, `NOT IN`,
   `!key`, `*` glob) becomes SQL / `jsonb` operators vs. a Go filter after a
   coarse GIN prefilter.
6. **Staged-operation bookkeeping** — whether re-shard / migration flows (`003.11`)
   need their own state tables (`reshard_operation`, …) or can be derived from
   `kafka_topic` rows.
7. **Optimistic token** — a plain `updated_at` compare vs. a dedicated
   `row_version bigint` (safe against same-instant writes).
