# Migration and Data Movement

Status: **draft**

Shapes: no dedicated proto yet — the orchestration state lives on `kafka_topic`
rows plus a `shard_migration` bookkeeping table (`003.12`). RPC surface TBD (see
Open questions).

The single flow behind every "a shard's data needs to end up somewhere else"
situation. It is on the critical path for:

- **Re-placement** — a placed shard whose cluster stopped matching the channel's
  affinity (`003.7` — auto-relocate).
- **`drain` taint** — evacuating every shard off a cluster (`003.7`).
- **Cluster delete with live topics** — the deferred `003.3` open question.
- **Re-sharding** — `channel_partitions` changes move key ranges between shards
  (`003.4`).
- **Governance** — the `franz.taint` / `franz.affinity/*` / `channel_partitions`
  actions (`003.8` OQ1a–c) all resolve to this flow.

## Model — drain-based migration

v1 does **no historical byte copy**. A migration moves the *serving position*, not
the bytes already written:

```
1. Provision   create the target shard topic on the destination cluster
               (same materialised config; agent reconciles it to READY)
2. Cut over    switch producer routing to the target; source stops taking
               new writes  (SetConsumption stays ENABLED on source)
3. Drain       consumers keep reading the source until its lag reaches zero
               (or a max-drain deadline)
4. Retire      SetConsumption(DISABLED) on source, then delete the source
               shard topic once no group has read it for a grace period
```

Consequences to accept for v1:

- **Unconsumed history on the source is only delivered if consumers drain it.**
  A group that is down for the whole migration and past the grace period loses
  access to messages that were on the source.
- **Re-partitioning is not retroactive.** After a re-shard, a key's *old* messages
  stay on whatever shard they were written to; only *new* messages follow the new
  shard map. Consumers must read all shards.
- Works only when consumer lag is bounded and drainable within the deadline.

Replication-based migration (MirrorMaker2 / a copy job, with offset translation)
is a **future option** for the cases where drain-based loss is unacceptable — see
Open questions.

## State

A `shard_migration` row per in-flight move: `kafka_topic_id`, `source_cluster`,
`target_cluster`, `phase` (`PROVISIONING` / `CUTOVER` / `DRAINING` / `RETIRING` /
`DONE` / `FAILED`), `started_at`, `drain_deadline`, `reason`
(`re-placement` / `drain-taint` / `cluster-delete` / `re-shard` / `governance:<policy>`).

The owning `kafka_topic` keeps its identity throughout; `kafka_cluster` flips to
the target at the **cut-over** step (step 2), so `state`/reconciliation already
track the new cluster while the old topic drains.

```
PROVISIONING ──target READY──▶ CUTOVER ──producers moved──▶ DRAINING
     │                            │                            │ lag=0 or deadline
     └── target fails ──▶ FAILED  └── fails ──▶ FAILED         ▼
                                                            RETIRING ──source gone──▶ DONE
```

## Safety

- **Idempotent phases.** Each phase is re-entrant; a crashed orchestrator resumes
  from the row's `phase`. No phase deletes data before the next is confirmed.
- **Source is never deleted while a consumer group has non-zero lag on it**,
  unless the `drain_deadline` passed *and* the migration reason permits forced
  retirement (cluster-delete does; re-placement does not — it stays `DRAINING`).
- **One migration per shard at a time.** A second trigger for a shard already
  migrating is queued, not started.
- **Rollback** is only clean before step 4: flip `kafka_cluster` back, restore
  producer routing, delete the (empty-ish) target. After retirement starts there
  is no rollback.
- Every phase transition is a signal record (`003.11`); governance-initiated
  migrations also write a `PolicyAction`.

## Open questions

1. **RPC surface** — is migration purely internal (triggered by placement /
   taints / governance), or is there an explicit `MigrateKafkaTopic` /
   `MigrateCluster` operator RPC? Re-shard specifically (`003.4` OQ2) needs an
   operator entry point.
2. **Data-copy mechanism** — keep drain-based only, or add replication-based
   (MirrorMaker2 vs. an agent-run copy job) with `__consumer_offsets`
   translation, selectable per migration? This is the biggest unknown and gates
   "lossless" migration.
3. **Drain deadline policy** — fixed, per-channel, or derived from observed lag;
   and what happens at the deadline for each reason (block vs. force vs. alert).
4. **Re-shard key redistribution** — whether v1 accepts "old messages stay on old
   shards" permanently, or a re-shard must also replay/repartition history.
5. **Cluster-delete force semantics** — `003.3`: does `DeleteKafkaCluster` with
   live topics auto-trigger drain migrations for all of them, or require an
   explicit `force` / prior drain taint?
6. **Concurrency limits** — max simultaneous migrations per cluster / fleet, so a
   `drain` taint or a broad governance match doesn't stampede.
