# Governance

Status: **draft**

Shapes & RPCs: [`governance.proto`](../../franz/api/franz/v1/governance.proto) —
`Policy`, `Matcher`, `Entity`, `Limit`, `Operator`, `Action`, `ActionKind`,
`PolicyAction`, `Indicator`, `GovernanceService` (Policy CRUD + `DryRunPolicy` +
`ListPolicyActions` + `Indicator` CRUD + `ListIndicatorSamples`). Indicator
samples arrive via [`telemetry.proto`](../../franz/api/franz/v1/telemetry.proto);
their ingest semantics are `003.14-telemetry-ingest.md`.

## Concepts

Governance lets an **Async Admin** attach fleet-wide rules that make Franz **react**
to how resources actually behave. A **Policy** watches one **Indicator**; when the
latest sample crosses a **Limit**, the policy runs its **Actions** on every
resource its **Matcher** selects.

**Reactive only — no admission control.** A policy never rejects or delays a
`Create` / `Update`. It observes an indicator and mutates Franz's *declared*
state after the fact; the normal reconciliation path (`003.6`) then realises the
change. The old "reject topic creation / update" actions are gone.

```
Telemetry Agent ──sample──▶ Indicator ──▶ Policy (limit crossed?)
                                              │ yes
                                     Actions mutate declared state
                                              │
                                     reconciliation realises it
                                              │
                                     PolicyAction recorded
```

## Key shapes

- **`Policy`** — `indicator` (name), `matcher`, `limit`, `actions` (ordered),
  `weight` (tie-break, higher wins), `enabled`, `last_fired_at`. `name` is the
  realm-unique key.
- **`Matcher`** — `entity` (`ASYNC_CHANNEL` / `KAFKA_TOPIC` / `KAFKA_CLUSTER`) +
  `selector` (a `003.1` label selector; empty = every resource of that entity).
- **`Limit`** — `operator` (`<`, `≤`, `=`, `≠`, `≥`, `>`) + `value`, a **string**
  encoded in the indicator's unit (`"150Gi"`, `"3"`, `"90d"`). A lower+upper band
  is two policies.
- **`Action`** — `kind` + positional `args`:

  | Kind | args |
  |---|---|
  | `ADD_LABEL` | `[key, value]` |
  | `REMOVE_LABEL` | `[key]` |
  | `SET_STATUS` | `[status]` |
  | `UPDATE_FIELD` | `[field, value]` |
  | `INCREASE_FIELD_BY` | `[field, amount]` |
  | `DECREASE_FIELD_BY` | `[field, amount]` |

  `amount` may be absolute or a percentage (`"50%"`). What an action may write is
  bounded by the **write whitelist** below.
- **`Indicator`** — `unit`, `applies_to` (entity), `source_agents`, `health`
  (`HEALTHY` / `STALE`), `last_sample_at`, `staleness_threshold`. **Pre-registered**
  by an admin (`CreateIndicator` / `UpdateIndicator` / `DeleteIndicator`) before
  any sample or policy can reference it (`003.14`). Samples are published by
  Telemetry Agents, never through `GovernanceService`.
- **`PolicyAction`** — the audit record of one automated change: `occurred_at`,
  `resource_orn`, `indicator_value`, `action`, `result`. Read via
  `ListPolicyActions`.

## Write whitelist

An action may only touch the `(entity, field, ops)` combinations below;
anything else is rejected at `CreatePolicy` / `UpdatePolicy`.

| Entity | Field | Allowed ops | Notes |
|---|---|---|---|
| `KAFKA_TOPIC` | `partitions` | `UPDATE_FIELD`, `INCREASE_FIELD_BY` | increase-only (`003.6`); per-policy hard cap |
| `KAFKA_TOPIC` | `replication_factor` | `UPDATE_FIELD` | ≤ target cluster broker count |
| `KAFKA_TOPIC` | `topic_configuration.<key>` | `UPDATE_FIELD`, `INCREASE_FIELD_BY`, `DECREASE_FIELD_BY` | `<key>` must be a real Kafka topic config key |
| `KAFKA_TOPIC` | `consumption` | `UPDATE_FIELD` | `ENABLED` / `DISABLED` — drains/undrains the shard |
| `KAFKA_TOPIC` | non-`franz.*` labels | `ADD_LABEL`, `REMOVE_LABEL` | |
| `ASYNC_CHANNEL` | `channel_partitions` | `INCREASE_FIELD_BY`, `DECREASE_FIELD_BY` | staged re-shard (`003.13`); per-policy cap |
| `ASYNC_CHANNEL` | `state` | `SET_STATUS` | `PAUSED` / `ACTIVE` / `DELETED` |
| `ASYNC_CHANNEL` | labels incl. `franz.affinity/*`, `franz.antiaffinity/*` | `ADD_LABEL`, `REMOVE_LABEL` | affinity edits trigger re-placement / migration (`003.7`, `003.13`) |
| `KAFKA_CLUSTER` | `state` | `SET_STATUS` | `PAUSED` / `ACTIVE` / `DELETED` |
| `KAFKA_CLUSTER` | `cluster_configuration.<key>` | `UPDATE_FIELD` | applies to *new* topics only (`003.3`) |
| `KAFKA_CLUSTER` | labels incl. `franz.taint` | `ADD_LABEL`, `REMOVE_LABEL` | `franz.taint` may be set to `no-creation` **or** `drain` |

`KAFKA_TOPIC.state` is **not** writable — a topic's state is derived / follows its
channel (`003.6`). `KafkaTopic` `SET_STATUS` is rejected.

## Evaluation

Evaluation is **event-driven**: a `PublishIndicatorSamples` call that updates the
current value for `(indicator, resource_orn)` (`003.14`) triggers, synchronously
or via an in-process queue, evaluation of every enabled Policy bound to that
indicator whose matcher selects that resource:

1. If the indicator is `STALE` (latest `sample_at` older than
   `staleness_threshold`) → **do not act**.
2. If `matcher.selector` matches the resource's labels → take the new value.
3. If `value <operator> limit.value` holds → the policy **triggers**.
4. Apply `actions` in order; record one `PolicyAction` per action; set
   `last_fired_at`.

**No cooldown / anti-thrash** — a policy re-fires as fast as samples arrive
(known gap, `003.8` chose to defer this until it is observed to be a problem;
`caps` on the `*_FIELD` actions are the only bound).

When more than one triggered policy targets the **same `(resource, field)`**,
they are applied in order of `(weight` desc`, name` asc`)` and the **last write
wins**; every action is still logged as a `PolicyAction`.

## Dry run

`DryRunPolicy` evaluates an **inline, unsaved** policy definition (`indicator` +
`matcher` + `limit` + `actions`; `weight` / `enabled` ignored) against the latest
samples and returns, per matched resource, the `indicator_value` and
`would_trigger`. It performs **no mutation** and writes **no** `PolicyAction`.

## Invariants

- `name` unique per realm; `matcher.entity ≠ UNSPECIFIED`;
  `limit.operator ≠ UNSPECIFIED`; `actions` non-empty; each action's `args` arity
  matches its `kind`.
- `indicator` must name a **registered `Indicator`** — `CreatePolicy` /
  `UpdatePolicy` referencing an unknown indicator is rejected (`003.14`).
- Every action must be in the **write whitelist** above — otherwise the policy is
  rejected at write time.
- `applies_to` and `matcher.entity` must agree — a policy cannot read a
  cluster-scoped indicator for a channel matcher.
- A disabled policy never triggers. A policy whose indicator is stale never
  triggers.
- Actions only ever change **declared** state; they never call agents directly and
  never touch access policies (`003.5`).
- `partitions` may only be raised (`003.6`); `SET_STATUS` values are limited to
  `PAUSED` / `ACTIVE` / `DELETED` (channel and cluster only).

## Cross-entity behavior

- **Targets** — `ASYNC_CHANNEL` (`003.4`), `KAFKA_TOPIC` (`003.6`),
  `KAFKA_CLUSTER` (`003.3`).
- **Migration flow** — `franz.affinity/*` / `franz.antiaffinity/*` edits on a
  channel, `franz.taint` (`drain`) on a cluster, and `channel_partitions` changes
  all resolve to the migration flow (`003.13`); until it lands, these actions
  queue work that does not execute.
- **Indicators** — the console Governance landing page reads `ListIndicators`
  (count, `health`, `last_sample_at`) above the policy list; ingest is `003.14`.
- **Reconciliation** — a policy that changes `topic_configuration` or
  `partitions` produces the same effect as an operator edit: the shard goes
  `READY → PENDING → READY`.
- **Auditability** — every automated change is a `PolicyAction`; there is no
  silent mutation.

## Open questions

1. **Per-action caps** — the concrete cap encoding for `INCREASE_FIELD_BY` /
   `DECREASE_FIELD_BY` (absolute ceiling, max delta per fire, floor) — the only
   bound on repeated firing given no cooldown.
2. **Anti-thrash** — deliberately deferred (no cooldown / hysteresis). Revisit
   when flapping or fleet churn is observed in practice.
3. **Dry run of a saved policy** — allow `DryRunPolicy` by policy `name`, and add
   a `simulated_effect` showing the resulting field values, not just
   `would_trigger`.
4. **Range limits** — keep two-policy bands, or add a range / `BETWEEN` operator.
5. **`topic_configuration` / `cluster_configuration` key set** — whether every
   Kafka config key is writable or a curated subset (e.g. exclude `cleanup.policy`
   and other semantics-changing keys).
