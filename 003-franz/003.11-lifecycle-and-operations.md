# Lifecycle and Operations

Status: **draft**

Shapes & RPCs: spread across `../../franz/api/franz/v1/` — pause/resume and delete on
`async_channel.proto`, `kafka.proto` (`KafkaClusterService`), `agent.proto`;
`SetConsumption` on `kafka.proto`; `PolicyAction` / `ListPolicyActions` on
`governance.proto`.

This document coordinates **cross-entity operational flows**. Each entity's own
state machine lives in its `003.x` doc; here is how they compose.

## Pause / resume

| Entity | RPCs | Paused means | Propagation |
|---|---|---|---|
| Kafka Cluster (`003.3`) | `PauseKafkaCluster` / `Resume` | excluded from **new** placement | existing shards untouched and still reconciling |
| Async Channel (`003.4`) | `PauseAsyncChannel` / `Resume` | Franz stops reconciling the channel's shards | every shard → `KafkaTopic` `PAUSED` |
| Agent (`003.9`) | `PauseAgent` / `Resume` | Franz hands it no work | none (exact scope is an open question in `003.9`) |

Pause is always reversible and never removes real-world resources. Kafka Topic has
no independent pause — it follows its channel.

## Soft delete and retention

`DeleteX` on a Kafka Cluster, Async Channel, Kafka Topic, or Agent is a **soft
delete**: the record moves to a terminal `DELETED` state, is retained for audit,
and its `name` / FRN is **never freed**. Any further operation on it returns
`FAILED_PRECONDITION`.

- **Async Channel delete** cascades: every generated Kafka Topic → `DELETED`, and
  agents remove the real topics.
- **Kafka Topic delete** happens only as a consequence of channel delete or a
  re-shard — there is no direct `DeleteKafkaTopic` RPC.
- **Client delete** (`003.10`) currently has no `DELETED` state field; the record
  is removed but the FRN is not reclaimed and FRN-matched access-policy statements
  go dormant. Aligning Client with the soft-delete model is an open question.
- Retention period for `DELETED` records, and whether they are ever purged, is an
  open question.

## Deletion with dependents

- **Kafka Cluster with live Kafka Topics** — rejected today with
  `FAILED_PRECONDITION`. A `force` / drain path builds on the migration flow
  (`003.13`); the exact trigger (auto-drain on delete vs. explicit `force` vs.
  require a prior `drain` taint) is `003.13` open question 5. Until then, drain the
  cluster first (taint `decommission:drain`, `003.7`) or delete the owning channels.
- **Agent named by a cluster** (`cluster_provider_agent`) — the link is an
  unvalidated string, so delete is *not* blocked today; whether it should be is an
  open question (`003.9`).
- **Async Channel with clients connected** — delete is not blocked; connected
  clients lose the data path when the shards are removed.

## Re-sharding and shard migration

Both are specified in **`003.13-migration-and-data-movement.md`**:

- **Re-sharding** — a `channel_partitions` change (`003.4`) adds or removes shard
  topics and shifts producer routing; removed shards drain then delete.
- **Shard migration** — moving one shard from cluster A to B, triggered by a
  `drain` taint (`003.7`), a misplaced shard after a label change (`003.7`), a
  governance placement action (`003.8`), or an operator.

v1 is **drain-based** — no historical byte copy; the serving position moves, not
the bytes already written. The old `cluster-migration` endpoint and `TopicRevision`
are gone.

## Consumption drain

`SetConsumption(DISABLED)` on a Kafka Topic (`003.6`) is the shared building block
for the flows above: producers stop routing to the shard, its `traffic_share`
goes to zero, consumers may finish, and the topic plus its data are retained until
an explicit delete. `SetConsumption(ENABLED)` reverses it.

## Signal and event history

What exists:

- **`PolicyAction`** (`003.8`) — every automated governance change, queryable per
  policy via `ListPolicyActions`.
- Per-entity `state` fields and the `updated_at` timestamp — current state, no
  history.

What does not exist: a general control-plane event log (state transitions,
reconciliation outcomes, operator actions, agent reports). Reconciliation failure
reasons (`003.6` open question 5) have nowhere durable to live yet. Designing this
is an open question.

## Open questions

1. **Soft-delete retention** — how long `DELETED` records are kept, whether they
   are ever purged, and whether `name` / FRN can eventually be reused.
2. **Client and the soft-delete model** — give `Client` a `DELETED` state for
   consistency, or keep it a hard delete with a reserved FRN.
3. **Migration RPC surface + data-copy mechanism** — tracked in `003.13`
   (open questions 1–2): internal-only vs. operator RPC, and drain-based only vs.
   adding replication-based (MirrorMaker2 / copy job).
4. **Control-plane event log** — whether Franz persists a general history of state
   transitions, reconciliation outcomes, and operator actions, and its retention.
5. **Cascade on channel delete** — synchronous vs. best-effort; what the channel's
   `DELETED` means while its shards are still being removed.
