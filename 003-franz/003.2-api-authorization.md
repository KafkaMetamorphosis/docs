# API Authorization

Status: **open — not yet decided**

Shapes & RPCs: no proto yet. When decided, enforcement will sit at the gateway /
gRPC interceptor, ahead of every `*Service` handler in `../../franz/api/franz/v1/`.

> **This document is a placeholder.** The authorization model for console / API
> callers is **not decided**. Nothing below is normative — it only frames the
> problem and records the options. Do not implement against it.

## Scope

This concerns how Franz authorizes **console / API callers** — a human or a
machine token invoking the gRPC / REST API. It is **distinct** from
`003.5-access-policy.md`, which decides whether a **Client** may read or write an
Async Channel on the data plane. `003.5` is decided; this is not.

**Authentication** — how a caller proves identity, token issuance, IdP
integration — is a separate concern with its own ADR, also not yet written.

## What is assumed (and not open)

- A caller is authenticated and acts within exactly one **realm** (`003.1`); an
  FRN carries its realm, so a realm-A credential can never name a realm-B
  resource.
- Authorization is checked **before** the handler runs, centrally, not per
  handler.
- Failures surface as gRPC `PERMISSION_DENIED`; missing / invalid credentials as
  `UNAUTHENTICATED`.

Everything else below is undecided.

## Open questions

1. **Permission unit** — coarse `<resource>:<verb>` scopes (e.g.
   `async-channel:write`), per-method permissions, roles + bindings as
   first-class Franz resources, or attribute/policy-based rules.
2. **Verb granularity** — if scopes: `read` / `write` only, or a finer
   `create` / `update` / `delete` / custom-method split.
3. **Resource set & grouping** — one permission surface per service, or
   grouped (e.g. Kafka Topic operations under Async Channel); how
   `SetAccessPolicy`, `SetConsumption`, `Pause`/`Resume` are classified.
4. **Resource-scoped grants** — whether a grant can be narrowed to an FRN or
   FRN glob (IAM-policy style), and how that interacts with `List` (filter
   results vs. reject the call).
5. **Telemetry / agent calls** — `TelemetryService` and any future agent-facing
   RPCs are almost certainly authorized by agent credentials rather than user
   scopes; confirm and specify where that boundary is drawn (agent interaction
   ADR).
6. **Platform / cross-realm access** — a super-scope for operators managing many
   realms; interaction with realm provisioning (`003.1`).
7. **Representation** — opaque token claims vs. a Franz-managed role model;
   overlaps the authentication ADR.
8. **Personas** — once the model exists, document non-normative starting grants
   for the Async Admin, service teams, fleet operators, auditors.
